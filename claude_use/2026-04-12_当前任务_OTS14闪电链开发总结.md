# 2026-04-12 当前任务 OTS14闪电链开发总结

## 当前结论

OTS14 闪电链目前已经落到可用版本，核心链路为：

1. `commandskill.as` 只负责施法动画、音效和生成 starter 弹头
2. `chain_lightning_starter.projectile` 通过 `notify_script` 回调脚本
3. `GFLskill.as` 在 `result_event` 中做一次 `getCharactersNearPosition(...)` 快照查询
4. 查询结果组装为 `ChainEffectDefinition + candidate snapshot`
5. `GFLtask.as` 中的 `ChainTask` 负责后续纯内存跳跃
6. 每跳分别触发：
   - 伤害弹头
   - 命中特效弹头
   - 连接两点的 link 弹头

## 这次开发中确认失败的方向

以下方向已经实测不适合作为 OTS14 当前实现主线：

- 在 `/skill -> commandskill.as` 当前调用链中直接做 `getCharactersNearPosition(...)`
- 用 `send(make_query class="characters" ...)` 走异步 nearby-character 查询
- 把 nearby-character 同步查询简单挪到 bootstrap task / phase task 中

现象分别是：

- 直接同步查会卡在 `waiting for response for the query...`
- 异步 `characters make_query` 没有稳定收到 `query_result`
- task 中同步查在 OTS14 这条路径下也未证明安全

因此最终确认：  
对 OTS14 这类连锁技能，附近目标快照应放在已验证可工作的 `notify_script -> GFLskill.as` 上下文中完成，而不是继续强行塞回 `commandskill.as` 或 task update。

## 这次开发中确认可行的方向

### 1. 单次快照 + 纯内存后续

这是当前最稳的实现方式。

优点：

- 只查一次附近敌人
- 后续跳跃不再依赖 query
- 跳数、距离、重复传导等规则都能集中在 `ChainTask` 中控制

适用前提：

- 链持续时间短
- 候选数量受限
- 可接受后续跳跃使用快照位置而非实时位置

### 2. `notify_script` 作为安全查询上下文

这次开发的关键结论不是“`notify_script` 更优雅”，而是“它在当前工程里更稳定”。  
OTS14 目前就是依赖 starter 弹头先落地，再在 `GFLskill.as` 的 `result_event` 中完成快照查询。

### 3. 每跳命中特效必须走保守模板

链逻辑稳定后，真正的崩溃点出在每跳命中特效弹头。

验证结果：

- 只生成伤害弹头时，链稳定
- 恢复旧的 `chain_lightning_hit_effect.projectile` 后，游戏会再次原生崩溃
- 即使只保留 `thunder.wav`，旧写法仍不稳定
- 将 `chain_lightning_hit_effect.projectile` 改成类似 `para_heal_effect_on_target.projectile` 的保守写法后恢复稳定

因此当前规则是：

- 高频重复生成的命中特效弹头，优先使用 `particle.projectile` 体系那种安全模板
- 不要直接复用大爆炸、重闪电、未验证材质链的“重表现”写法

## 当前版本的特效职责拆分

### starter

`chain_lightning_starter.projectile`

职责：

- 首次落点表现
- 触发 `notify_script`

特点：

- 只生成一次
- 可以容纳相对更重一点的闪电表现

### hit effect

`chain_lightning_hit_effect.projectile`

职责：

- 每跳目标点命中反馈

特点：

- 高频生成
- 当前使用 `para_heal_effect_on_target` 风格安全模板

### link effect

`chain_lightning_link.projectile`

职责：

- 连接每一跳的起点和终点

特点：

- 参考了 `OBR knife` 的“飞行表现弹头”思路
- 通过 `CreateProjectile_H(...)` 真正从 `fromPos` 飞到 `toPos`
- 使用低抛物线、较快速度、轻 trail

## 本次开发中遇到的典型问题与对应解决方法

### 问题 1：同步 nearby query 卡死

表现：

- 日志停在 `waiting for response for the query...`

解决：

- 放弃在 `/skill` 调用链和通用 bootstrap task 中做 nearby sync query
- 改为 starter projectile -> `notify_script` -> `GFLskill.as` 中做一次快照查询

### 问题 2：异步 `characters make_query` 没有回包

表现：

- 发出了 `make_query class=characters`
- 但没有收到对应 `query_result`

解决：

- 不再把它视为可靠能力
- 直接放弃该路线

### 问题 3：`getCharactersNearPosition(...)` 返回元素位置不可靠

表现：

- 候选存在，但 `position = 0 0 0`
- 导致链找不到下一跳

解决：

- nearby query 结果只拿 `id`
- 再用 `getCharacterInfo2(...)` 读取真实坐标并填入快照

### 问题 4：每跳命中特效导致原生崩溃

表现：

- 链逻辑正常
- 一恢复旧的 hit-effect projectile 就直接崩

解决：

- 把 `chain_lightning_hit_effect.projectile` 改成 `para_heal_effect_on_target` 风格写法
- 使用 `blast 0 damage + time trigger + rotation none + terrain/copy`

### 问题 5：连接两点的特效最初只是“在终点炸一下”

表现：

- arc projectile 没有真的连接两点
- 视觉上只是目标点多一个特效

解决：

- 新增 `chain_lightning_link.projectile`
- 在 `ChainTask.applyVisual()` 中用 `CreateProjectile_H(...)` 从 `fromPos` 飞到 `toPos`

### 问题 6：link 弹头飞到目标上空

表现：

- 轨迹没有落到目标位置，而是悬在上方

解决：

- 让脚本 `CreateProjectile_H(...)` 的 `gspeed` 与弹头 `pulldown_in_air` 保持一致
- 当前已调整为一致参数
