# 2026-04-12 历史记录 OTS14闪电链异步查询失败复盘

## 结论

本轮探索确认：

- `players` / `character` 的同步 `getComms().query(...)` 正常
- `characters` 的异步 `send(make_query)` 在当前环境下没有稳定回包
- 因此 “首查异步 query, 后续纯内存” 这条实现路线目前不成立

当前更可信的落地方案应改为：

- 技能入口只负责表现和投递启动任务
- 启动任务延迟一小帧后，用同步 `getCharactersNearPosition()` 做一次候选预收集
- 候选收集完成后启动纯内存 `ChainTask`
- `ChainTask` 后续不再发 query

## 本轮现象

日志中可以稳定看到：

- `/skill` 触发后，`players` 查询有回包
- `character id=...` 查询有回包
- OTS14 初始音效和落点特效会正常播放
- 随后脚本发出 `make_query class=characters faction_id=1 ...`
- 但没有任何对应的 `query_result query_id=...`

说明当前问题不在于 `ChainTask` 本身，而在于异步 `characters` 查询没有完成。

## 已验证的错误判断

之前的判断是：

- 在 `commandskill.as` 中发异步 `make_query`
- 在 `handleQueryResultEvent()` 中收 `characters` 结果
- 收到候选后再启动 `ChainTask`

这套逻辑在结构上是干净的，但运行日志证明：

- `make_query class=characters` 没有像预期那样回到 `handleQueryResultEvent()`
- 至少在当前项目和当前引擎行为下，不能把它当作可靠路径

因此这个方向应视为一次失败探索，而不是继续追加修补的主线。

## 为什么看起来像“直接爆炸”

当前 OTS14 施法时会先生成：

- `chain_lightning_hit_effect.projectile`

这个弹头本身就是即时落点特效，所以即使后续连锁没有真正启动，视觉上也会先出现一次“落点爆闪”，看起来像技能只炸一下就结束了。

## 下一版推荐实现

推荐改成：

1. `excuteOTS14Skill()`
只做动画、音效、初始落点特效、组装 `ChainEffectDefinition`、投递 bootstrap task。

2. `DelayChainBootstrapTask`
延迟 `0.05 ~ 0.1s`，确保脱离 `/skill -> handleChatEvent` 当前调用链。

3. bootstrap task 内同步查询
在 task 的 `update()` 里按敌对阵营调用 `getCharactersNearPosition()`，只做一次候选收集。

4. `startChainEffectFromCandidates(...)`
把候选快照交给 `ChainTask`。

5. `ChainTask`
只做纯内存跳跃，不再 query。

## 可直接参考的现有实现

### 1. OBR knife

位置：

- `packages/GFL_Castling/scripts/trackers/GFLskill.as`
- `case 58`
- `case 59`

特点：

- 这是你印象里最接近“飞刀追踪”的现成实现
- 落点先生成一次伤害弹头
- 然后按敌对阵营同步 `getCharactersNearPosition()`
- 从候选里挑一个活目标
- 再用 `CreateDirectProjectile_T(...)` 发出追踪刀

对应关键调用：

- `spawnStaticProjectile(..., "skill_obr_knife_damage.projectile", ...)`
- `getCharactersNearPosition(...)`
- `CreateDirectProjectile_T(..., "skill_obr_knife_1.projectile", ...)`
- `CreateDirectProjectile_T(..., "skill_obr_knife_2.projectile", ...)`

这套实现不是多跳链，但很适合作为“落点吸附到一个目标再追过去”的参考。

### 2. UZI MOD3

位置：

- `packages/GFL_Castling/scripts/trackers/GFLtask.as`
- `class UZISkillTask`

特点：

- 明确是固定次数任务
- 初始等待后重复执行
- 注释里就是“共 3 次”
- 每次遍历锁定目标列表并在目标位置生成子弹头

对应构造：

- `super(metagame, cId, fId, pos, 1.5, 3);`

这说明工程里已经有“先锁一批目标，再分阶段重复打”的成熟写法。

### 3. HK416 / XM8

位置：

- `packages/GFL_Castling/scripts/trackers/GFLtask.as`
- `class HK416SkillTask`
- `class XM8SkillTask`

特点：

- `HK416SkillTask` 是“对已锁定列表反复结算”
- `XM8SkillTask` 是“任务内同步找附近目标，再按固定次数重复触发”

它们都说明：

- 这套工程更偏向 “Task + 同步收集 + 分段执行”
- 而不是 “异步 query 回调驱动整条技能链”

## 当前建议

后续如果继续做 OTS14 闪电链，优先参考：

1. `OBR knife` 的目标吸附方式
2. `UZI MOD3` 的固定次数 Task 结构
3. 当前已写好的 `ChainTask` 纯内存跳跃骨架

不要再继续把 `characters` 异步 `make_query` 作为主实现方向。

- 不能把异步 `characters make_query` 当作已验证可用能力
- 至少在当前 mod 环境下，应视为“不可靠”而不是“默认可用”

## 纯内存后续是否可行

结论：可行，但要接受它是“短生命周期快照驱动”的方案，而不是实时追踪方案。

可行的原因：

- 闪电链这类效果本身持续时间很短，通常只有几跳、总时长不到 1 秒到 1.5 秒
- 如果首轮候选在 bootstrap task 里一次性收集完成，后续只在快照里找最近目标，性能和稳定性都更好
- 项目里已有类似思路：
  - `UZISkillTask`：先锁目标列表，再固定次数重复结算
  - `HK416SkillTask`：对预先持有的目标列表重复执行

需要接受的限制：

- 后续跳跃使用的是“候选快照中的位置”，不是实时位置
- 目标如果在这段时间内移动较大，表现会有轻微误差
- 因为不再实时 query，后续跳跃不适合做特别长时间、特别远距离、特别依赖精确追踪的效果

对 OTS14 这种技能来说，这些限制是可以接受的。  
如果未来要做持续数秒、目标高速位移、每跳都要求实时锁定的链式效果，那才需要重新评估是否要用别的实现模式。
## 2026-04-12 补充结论

最终落地没有继续走 `commandskill.as` 或 `DelayChainBootstrapTask` 里的 `characters` 查询。

当前改成：

- `commandskill.as` 只负责 OTS14 施法表现，并生成 `chain_lightning_starter.projectile`
- starter projectile 通过 `notify_script key="ots14_chain_scan"` 把落点事件送到 `GFLskill.as`
- `GFLskill.as case 68` 在落点半径 `20.0f` 内执行一次 `getCharactersNearPosition(...)`
- 这次查询得到的候选列表会交给 `startChainEffectFromCandidates(...)`
- 后续连锁跳跃只由 `ChainTask` 基于这次快照继续执行，不再实时查询

这说明当前工程里更安全的结论是：

- `getCharactersNearPosition()` 仍可用
- 但更适合放在已经被现有技能验证过的 `notify_script -> handleResultEvent` 上下文里
- 不要继续强行把附近角色查询塞回 OTS14 的 `/skill` 入口或它派生出来的 bootstrap task
