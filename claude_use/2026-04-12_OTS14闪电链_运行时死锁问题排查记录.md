# 2026-04-12｜OTS-14 闪电链｜运行时死锁问题排查记录

## 当前状态

编译可以通过，但进入游戏后触发 OTS-14 闪电链技能时，脚本会永久挂起。表现为：

- 引擎未崩溃
- 日志停在 `waiting for response for the query...`
- 后续没有 `received: query_result`

这说明问题更像是脚本侧的阻塞死锁，而不是引擎崩溃。

## 当前实现路径

当前 OTS-14 的触发路径大致为：

```text
/skill
  -> CommandSkill::handleChatEvent()
    -> getPlayerInfo()
    -> getCharacterInfo()
    -> getPlayerInfo()
    -> excuteOTS14Skill()
      -> triggerChainEffect()
        -> getCharactersNearPosition()
        -> 死锁
```

关键点不是“链逻辑写错”，而是“首目标或候选搜索仍然依赖同步范围 query，且发生在 `handleChatEvent` 调用链里”。

## 已确认的问题根源

`getCharactersNearPosition()` 的实现位于 `query_helpers.as`，内部使用：

- `metagame.getComms().query(query)`

这是同步阻塞式查询。

而当前 OTS-14 的 `triggerChainEffect()` 虽然改成了“预收集候选列表”，但预收集本身仍然在技能入口同步执行，仍然属于：

- `handleChatEvent`
- `excuteOTS14Skill`
- `triggerChainEffect`
- `getCharactersNearPosition`

也就是说，当前所谓“去掉 query 嵌套”只去掉了 `ChainTask` 里的 query，没有去掉技能入口链路里的同步范围 query。

## 为什么现在的两种修法都不够

### 失败方向 1

把 `chainFindNextTarget()` 从 `start()` 挪到 `update()`。

问题是：

- `tasker.add()` 当帧就可能触发任务启动
- 如果任务在当帧就进入查询逻辑，本质上仍未脱离当前回调栈

所以这不等于“脱离死锁环境”。

### 失败方向 2

在 `triggerChainEffect()` 里预收集候选目标。

问题是：

- `triggerChainEffect()` 仍由 `excuteOTS14Skill()` 直接调用
- `excuteOTS14Skill()` 仍运行在 `handleChatEvent()` 的同步调用链里

所以只是把 query 从链任务里搬到了技能入口里，没有解决上下文问题。

## 新的修正判断

正确的纠偏方向不是“把 query 换个函数放”，而是：

- **先脱离 `handleChatEvent` 当前调用栈**
- **下一帧再做首目标范围查询**
- **查询完成后再创建真正的 ChainTask**

这是“换时机”，不是“换位置”。

## 推荐修改方案

本记录中的“延后一帧再做同步 query”适合作为中间验证思路，但截至 2026-04-12 当前代码已进一步调整为更稳的终版方向：

- 首次目标搜索改为异步 `make_query`
- 在 `handleQueryResultEvent` 中接收 `query_result`
- 收到结果后再启动纯内存 `ChainTask`

因此，bootstrap 方案现已降级为历史分析路径，不再是优先实现方案。

### 总原则

OTS-14 技能入口里不要直接执行任何 `class=characters` 的同步范围查询。

### 推荐分成三个阶段

1. `excuteOTS14Skill()`

只负责：

- 校验冷却和施法条件
- 读取 `aim_target`
- 播放动画、音效、初始视觉
- 构造 `ChainEffectDefinition`
- 投递一个延迟启动任务

不要负责：

- `getCharactersNearPosition()`
- 候选列表预收集
- 首目标吸附

2. `PendingChainQuery + handleQueryResultEvent`

这是关键补丁层，负责：

- 发送 `class=characters` 的异步查询
- 记录本次待完成的链请求
- 在 `query_result` 返回时做首目标/候选搜索结果解析
- 构造 `ChainExecutionContext`
- 再投递真正的 `ChainTask`

3. `ChainTask`

只负责：

- 按跳推进
- 从已收集数据里选下一目标
- 执行伤害与特效

`ChainTask` 里继续保持“纯内存，不发 query”的原则。

## 建议的新调用链

```text
/skill
  -> handleChatEvent()
    -> excuteOTS14Skill()
      -> 播放施法表现
      -> send(make_query characters ...)
      -> 记录 PendingChainQuery

收到 query_result
  -> handleQueryResultEvent()
    -> 解析 characters
    -> 选首目标 / 组候选
    -> tasker.add(ChainTask(...))

再后续
  -> ChainTask.update()
    -> 纯内存推进连锁
```

## 为什么这个方案比当前方案更靠谱

它和当前失败方案的区别不在于“用了另一个函数”，而在于：

- 不在 `handleChatEvent` 当帧阻塞等待范围查询
- 不再依赖 `getComms().query()` 的同步接口
- 首次范围查询改为事件驱动的异步续流程

如果死锁真的是由当前回调上下文触发，这个方案才有机会绕开它。

## 关于 NytoBlack 的判断

当前不应继续把“NytoBlack 能用 `getCharactersNearPosition`”视为 OTS-14 也能直接照抄的证据。

更合理的判断是：

- NytoBlack 可能恰好没有命中会触发死锁的上下文
- 或者其查询路径、时序、数据量和 OTS-14 并不完全一样
- 它可以参考，但不应继续作为 OTS-14 现方案成立的前提

## 当前最推荐的下一步

1. 把 `triggerChainEffect()` 里的同步预收集降级为历史实现，不再作为 OTS14 入口。
2. 在 `commandskill.as` 中增加 `PendingChainQuery`。
3. 在 `excuteOTS14Skill()` 里发送异步 `make_query characters`。
4. 在 `handleQueryResultEvent()` 中解析返回结果并组装候选列表。
5. 通过“纯内存入口”创建 `ChainExecutionContext` 并交给 `ChainTask`。

## 如果一帧后启动仍失败

再考虑第二优先级方案：

- 完全改成显式异步 query 状态机
- 不再使用 `getComms().query()` 阻塞接口
- 而是用 `send + query_result 事件回调` 分步推进

但这应放在“一帧后启动”尝试失败之后，因为实现复杂度明显更高。

## 结论

当前 OTS-14 实现偏掉的核心，不是“用了 query”本身，而是：

- 在技能入口同步调用链里做了范围 query
- 以为把 query 从 ChainTask 内挪走就等于脱离了问题

真正该改的是：

- 让技能入口只负责投递
- 让范围查询延后一帧执行
- 再让 ChainTask 处理后续纯内存连锁
