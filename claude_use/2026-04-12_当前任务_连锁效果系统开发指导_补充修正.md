# 2026-04-12 当前任务 连锁效果系统开发指导 补充修正

## 本次修正结论

此前文档中曾把“异步 `characters make_query` + `query_result` 回调初始化”视为推荐主线。  
结合当前项目实测日志和 `_ori_RunningWithRifles` 原版脚本核对，这个判断需要修正。

当前更稳的推荐主线是：

- 技能入口只做动画、音效、初始特效、参数组装
- 用 bootstrap task 延迟一小帧，脱离 `/skill -> handleChatEvent` 当前调用链
- 在 bootstrap task 里按敌对阵营同步 `getCharactersNearPosition()`
- 只做一次候选预收集
- 把候选快照交给 `ChainTask`
- `ChainTask` 后续只做纯内存推进，不再继续 query

## 为什么要修正

已确认现象：

- 同步 `players` / `character id=...` 查询正常
- OTS14 中异步发出的 `make_query class=characters` 没有稳定得到对应 `query_result`
- 在原版 RWR 脚本中，也没有找到一个已验证可用的“异步 nearby characters 查询”样例

因此当前更合理的工程判断是：

- 不把异步 `characters make_query` 当作可靠能力
- 把它视为一次失败探索，而不是继续追加修补的主线

## 纯内存后续是否可行

结论：可行，但适用于“短生命周期链式效果”。

适用前提：

- 总跳数有限
- 总时长较短
- 候选列表有上限
- 可以接受目标位置来自首轮快照，而不是每跳实时重查

为什么可行：

- 闪电链本身通常只持续很短时间
- 一次性收集候选后，后续纯内存推进更稳、更省 query
- 项目里已有类似思路：
  - `UZISkillTask`：先锁目标列表，再固定次数重复结算
  - `HK416SkillTask`：对预先持有的目标列表重复执行

需要接受的限制：

- 目标位移较大时，后续跳跃可能略有偏差
- 不适合做持续很久、每跳都要求实时锁定的链式效果

对 OTS14 这类技能，这个取舍是合理的。

## 对 OTS14 的当前推荐实现

推荐链路：

1. `excuteOTS14Skill()`
只做施法表现和配置组装。

2. `DelayChainBootstrapTask`
延迟 `0.05 ~ 0.1s`。

3. bootstrap task 内同步首查
按敌对阵营做一次 `getCharactersNearPosition()` 候选收集。

4. `startChainEffectFromCandidates(...)`
把候选快照交给连锁系统。

5. `ChainTask`
后续纯内存跳跃推进。
