# GFL-Castling 技能系统 Task 迁移路线

## 目标

本文档用于记录技能系统从“手动 tracker 数组 + update 遍历”迁移到 Task 体系的统一路线。

迁移目标是降低技能实现的重复代码、明确状态归属，并让 Task 成为项目内延时和多阶段逻辑的主执行模型。

## 基本原则

### 保持外部路由不变

迁移过程中，以下外部入口尽量保持不变：

- `commandskill.as` 中的 `commandSkillIndex + switch`
- `GFLskill.as` 中的 `gameSkillIndex + switch`

也就是说，优先重构 case 内部实现，不优先重写整个分发框架。

### 保持技能效果不变

迁移目标是架构收敛，不是玩法重做。

需要尽量保持以下行为一致：

- 弹头类型
- 伤害与范围
- 触发时机
- 执行次数
- 间隔时间
- 搜索范围
- 额外音效或视觉效果

### 一次只处理一种模式

优先迁移重复模式明显、风险较低的技能，不要在一个提交里同时处理多种完全不同的技能机制。

## 迁移分层

### 第一优先级：状态归位

先把已经用了 Task、但状态仍然散落在多个文件里的技能收束到单独模块。

典型对象：

- M14MOD3

目标是让这类技能拥有清晰的单点状态归属，不再依赖分散的全局变量。

### 第二优先级：重复效果抽象

把旧式“数组里存状态、update 定时执行 N 次”的技能模式统一抽成通用 Task 基类。

建议方向：

- `RepeatEffectTask`

适用场景：

- 固定间隔重复触发
- 重复次数固定
- 每次执行逻辑相似，只是目标或参数不同

### 第三优先级：逐个 case 迁移

通用基类稳定后，再将具体技能逐一迁移到 Task。

推荐顺序：

1. DOT 类
2. XM8
3. HK416
4. UZI
5. 其他重复模式技能

### 第四优先级：复杂状态机技能

等重复模式迁移成熟后，再处理不适合 `RepeatEffectTask` 的技能，例如：

- Javelin
- 充能技能
- 多阶段变身技能

这类技能通常需要独立 Task 组合或专用 tracker，而不是通用重复效果模板。

## 建议的迁移步骤

每迁移一个技能，建议按以下顺序进行：

1. 在 `GFLtask.as` 中新增或补充对应 Task。
2. 修改 `commandskill.as` 或 `GFLskill.as` 的对应 case，使其改为创建 Task。
3. 删除旧的 tracker 数组写入逻辑。
4. 删除旧的 `update()` 遍历逻辑。
5. 删除不再使用的 tracker 类定义。
6. 检查是否还有跨文件状态残留。

## 完成标准

一个技能完成迁移后，应满足：

1. 运行效果与迁移前一致。
2. 原先对应的 tracker 数组和 `update()` 片段已经消失。
3. 主要状态已经收敛到 Task 或独立 tracker。
4. 分发层没有新增新的耦合。

## 与工具链的关系

迁移不是纯运行时代码工作，建议和 `tools/` 里的分析脚本配合推进。

后续可补充的自动化项：

1. 哪些 passive case 仍然依赖旧 tracker。
2. 哪些 case 已经切换到 Task。
3. 哪些技能仍然依赖跨文件全局状态。
4. 技能映射、弹头映射、notify key 是否完整。

## 当前结论

从现有资料看，技能系统的方向已经明确：

- `TaskManager` 是应继续强化的主干
- `commandskill.as` / `GFLskill.as` 应逐步薄化
- `kill_event.as` 不应继续承载过多技能专有状态
- `tools/` 和正式文档应一起维护迁移进度

这份文档只记录迁移路线，不记录实时进度。实时进度应通过报告或工具产物更新。
