# GFL-Castling 技能实现最佳实践

## 目标

本文档用于约定当前项目在新增或维护技能实现时的推荐写法。

目标不是强行重构为统一架构，而是在保留现有制作习惯的前提下，逐步降低维护成本。

## 当前原则

项目当前没有必须立刻推进的系统级大迁移。

因此，后续工作的重点不是“全面重构”，而是：

1. 保持现有开发节奏
2. 避免继续堆高大文件复杂度
3. 在新增和顺手维护时，逐步把复杂逻辑收敛成更清晰的结构

## 总体思路

### 1. 保留 switch/case，但让它更像分发层

当前项目可以继续使用 `switch/case` 作为技能入口。

推荐做法：

- `case` 内只做参数读取、轻量校验、调用函数
- 不在 `case` 内继续堆太长的实现逻辑

推荐形态：

```as
case 85: {
    excuteM14MOD3Skill(characterId, playerId, modifer);
    break;
}
```

不推荐形态：

```as
case 85: {
    // 在 case 内直接写几十行甚至上百行实现
    // 同时处理状态、表现、清理、冷却、联动
    break;
}
```

### 2. 专属特判允许存在，但尽量命名化

项目中不可避免会有很多“某个角色/某个武器专属特判”。

问题不在于特判本身，而在于特判是否散落成难以理解的匿名代码块。

推荐做法：

- 把专属逻辑提成有名字的小函数
- 函数名直接表达业务意图

例如：

- `handleM14KillChain(...)`
- `applyNagantKillCooldownBonus(...)`
- `handlePPKMod3KillStage(...)`

这样即使逻辑还在同一个文件里，也更容易维护。

### 3. 复杂技能按状态归属决定落点

不要为了统一风格而把所有技能都塞进同一种结构。

推荐按以下方式选择：

- 即时、一次性技能：可留在 `commandskill.as`
- 延时、重复、多阶段执行：优先使用 `Task`
- 独立状态机：使用专用 `Tracker`
- 击杀联动技能：入口可留在 `kill_event.as`，实现尽量提成小函数或专用处理单元
- 轻量玩家状态：优先复用 `GFLplayerlist.as` 中的 tag / counter

核心原则：

状态放在最自然的归属处，不为了形式统一而额外制造结构。

### 4. 同类分支优先参数化，不优先复制

如果多个分支的差别只有少量参数，例如：

- 冷却时间不同
- marker 范围不同
- 调用的 task key 不同
- 延时和变种参数不同

则优先考虑：

- 抽成同一个辅助函数
- 只把差异作为参数传入

这样可以减少复制粘贴导致的维护成本和漏改风险。

### 5. 先抽同文件小函数，再决定是否拆文件

当前项目最适合的收敛顺序不是“先拆模块”，而是：

1. 先把长逻辑从 `case` 中提成同文件小函数
2. 当一组函数明显形成独立子系统时，再考虑拆成新文件

这样既不打断当前制作习惯，也能逐步提升可读性。

## 针对三个主要文件的建议

### commandskill.as

适合继续放：

- 简单主动技能
- 冷却检查
- 技能入口分发

不建议继续放：

- 多阶段状态机的大段实现
- 复杂击杀联动
- 长期运行时专属状态

### call_event_handler.as

适合继续放：

- call/event 入口
- 轻量参数整理
- 对已有 Task 的启动

不建议继续放：

- 大段专属业务逻辑
- 新的复杂状态系统
- 难复用的专属分支复制

### kill_event.as

适合继续放：

- `character_kill` 入口
- 击杀奖励
- 连杀结算
- 回甲/回甲窗口
- 轻量 on-kill 分发

不建议继续放：

- 越来越多完整技能实现直接堆在主流程里
- 清理、奖励、技能状态混杂成大段专属特判

## 新增代码的最低约束

后续新增技能时，建议至少遵守以下规则：

1. 简单技能可以继续直接写在入口文件里
2. 一个 `case` 如果已经明显过长，先提成小函数
3. 出现持续状态、延时执行、多阶段逻辑时，优先考虑 Task 或专用 Tracker
4. 出现击杀联动时，入口可留在 `kill_event.as`，但尽量不要把完整实现直接堆进去
5. 改动状态流或架构落点后，同步更新文档

## 结论

当前项目最理想的实践，不是全面重构，而是：

- 保留现有主工作流
- 保留 `switch/case`
- 逐步把大 `case` 变成薄分发层
- 逐步把复杂专属特判变成有名字的小处理单元

这套做法最适合当前项目的节奏，也最容易长期执行。
